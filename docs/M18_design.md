# M18 设计：对话式任务闭环（协商式管线 + 假设验证 + 线程总结）

> 创建：2026-08-25。触发：用户对当日实践的总结与系统方向指示。
> 前置证据：H3 五臂弧（A/B/C/D/E）+ 裁决 #3/#4 + 用户假设（i2v）验证成立——
> 当日最大突破来自**用户假设**而非系统搜索，反馈交流机制应升为一等系统组件。

## 0. 问题陈述（当日实证）

| 案例 | 暴露的缺口 |
|---|---|
| 用户提"两图无缝转场"（跨空间图对） | 目标在 fl2v 范式内不可达；系统是**事后**才发现（五臂 + ~15 币），应**先验**告知 |
| 裁决 #4 "A 最好，BC 完全割裂" | 机器指标（边界 MAD 0.0074）与感知相反；维度级裁决信息量大但只进了自由文本 |
| 用户假设"不如首帧文生视频" | 验证成立并升格为决策规则——这类输入是最高价值反馈，现路由器无此分类 |
| 五臂实验跨多个脚本/会话 | 上下文靠 STATUS.md + 人肉维持；长任务应有线程一等对象 |
| 当日手动写总结 | 线程收口的知识总结应自动化草拟、用户确认后入库 |

## 1. 用户决策（2026-08-25，本设计的边界条件）

1. **提示明确性**：生图/视频有专业性，用户需要学习才能提出合理需求——系统给的
   提示与建议必须**明确、可比较、带理由**（不是内行黑话）。前提=外部研究通道
   已完成（AI 须了解最新技术发展才能给建议）；**允许有技术认知的用户反向提出
   技术方向，AI 负责搜索与验证**（假设一等化，见 §4）。
2. **默认软提示**：命中边界/负模式时不强拦截——默认按推荐路径继续，路径卡片
   可展开查看与切换。强拦截仅保留一种情况：**已知必败模式**（negative_result
   直接命中且无成功先例，如"指令生成中间帧救 fl2v"）也只标红警示，不锁死
   （用户可能有探索意图，硬币是用户的）。

## 2. 架构：从"生成管线"到"协商管线"

```
现:  需求 → 规划 → 执行 → 评审 → 反馈(verdict) → 修订 → 终态
M18: 需求 → [前置可行性检查: boundary_laws ∨ decision_rules ∨ negative_result]
        → 路径卡片(软提示, 2-3 张: 效果预期/硬币/风险/边界注记/为什么)
        → 执行 → 评审(方差置信标注) → 解释器(机制+指标+证据链接+为什么不选X)
        → 反馈(五分类: +hypothesis) → 假设验证管线 → 规则升格(带署名)
        → 线程收口 → 四栏自动总结(用户确认入库)
全程挂 task_threads(长任务上下文)
```

## 3. 数据层（`kb/schema_m18.sql`，幂等；种子=`migrate_m18.py`）

- **boundary_laws**：statement / evidence / applies_to_json(family, task_facet)
  / alternatives_json / status(law→refuted 可修正——#1912 先例)
  种子：感知连续性三定律、二态切换机制、fl2v 决策规则（i2v 默认）、
  画幅跟随条件帧、GFPGAN U 型律、渲染一致律。
- **decision_rules**：conditions_json → route(推荐路径+参数) / rationale /
  source(kind: user_hypothesis|experiment|community, attribution)
  种子：跨空间图对→i2v+动作脚本（attribution=用户 2026-08-25）。
- **task_threads**：goal(原始表述) / real_need(协商后) / constraints_json /
  status(open→running→negotiating→closed) / summary_id；`webtasks.thread_id` 挂接。
- **user_hypotheses**：source(ruling_id|feedback) / statement / status
  (proposed→testing→verified|rejected) / verify_task_ids / verified→
  decision_rule_id 链。
- **thread_summaries**：facts / laws / rules / open_questions 四栏 +
  status(draft→confirmed)。

不建的表：会话消息日志（webapp 内存+task.json 已够，避免 DB 膨胀）；
提示词模板表（先硬编码在卡片生成器，≥3 个任务族出现重复再抽象）。

## 4. 编排层（`webapp/orchestrator.py` 增量）

1. **前置检查**（`_run_task` 规划前，新 `kb/boundaries.py`）：
   任务特征词法+LLM 分类 → 命中 boundary_laws/decision_rules/negative_result
   → 生成路径卡片（不阻塞，默认按推荐路径走，卡片随任务态下发前端）。
2. **卡片文案规范**（用户决策①的落地）：每张卡片四行——
   `做什么`(白话) / `预期效果与代价`(硬币+质量预期) / `已知风险`(引用定律
   编号+一句话人话版) / `什么情况下选它`。禁止未解释的术语。
3. **解释器升级**（final 态）：现机制解释 + 方差置信标注（exp015 规则：单次
   差异<0.05 标"噪声区间"）+ 证据链接（画廊/帧带/曲线 JSON）+ "为什么不是 X"
   （引用被否路径的 negative_result）。
4. **反馈路由 +假设类**（`kb/feedback.py` 五分类）：hypothesis →
   自动排探针（先零硬币可行性检查，花币需用户确认——软提示同样适用）→
   verified 起草 decision_rule（带 attribution）→ 用户确认入库。
   用户技术方向类输入（"用 LoRA X 试试"/"搜搜有没有 inpaint 方案"）同样走
   此通道：AI 负责检索（M11 三源/M17）+ 验证，不因"不符合当前认知"拒收。
5. **线程上下文**：线程内全部任务/裁决/知识写入对规划 LLM 可见（拼入 system
   prompt 的 thread_digest，超长按时间近者优先+定律/规则全保留）。
6. **持久化**：线程+任务态落 `data/threads/*.json`，重启恢复到 negotiating/
   review 等等待态（运行中任务标记 stale 需人工续）。

## 5. 前端（`webapp/static/index.html`，保持零依赖）

- **线程视图**：任务时间线（含每任务的臂/指标/裁决/卡片选择记录）。
- **路径卡片区**：规划阶段展示（软提示：默认路径高亮+倒计时 8s 自动继续，
  点其他卡即切换）。
- **结构化裁决 UI**：维度级（各输出×各维度 好中差 + 逐维一句话理由 +
  自由文本假设框——"我觉得不如试试 X"直接进 hypothesis 管线）。
- **Why 面板**：结论旁挂定律引用（编号+人话版）+ 证据链接。
- **收口总结卡**：四栏草稿可编辑，确认后写 thread_summaries + KB。

## 6. 验收标准（用户已确认 2026-08-25）

1. 回放 H3 弧为线程：五臂+两裁决+三定律在时间线完整呈现（用现有产物数据）。
2. 新用户提"跨空间两图无缝转场" → 软提示路径卡片（i2v 推荐 + fl2v 标注
   三定律风险 + 遮挡转场备选），默认 8s 后按 i2v 走，用户可换。
3. 用户经反馈 UI 提交假设 → 零硬币预检 → 花币确认 → 验证 → 带署名规则入库。
4. 线程收口 → 四栏总结确认 → KB 增量≈当日手动总结的自动版。
5. 卡片文案抽查：非技术用户可读懂（无未解释术语，硬币/风险/理由齐全）。
